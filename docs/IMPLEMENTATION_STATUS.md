# SimSuite implementation status

Last updated: 2026-08-08

## Current product state

SimSuite is in a **review, preview, validation, and dry-run** phase. The app has substantial scanning, indexing, inspection, duplicate review, Downloads/Inbox, Updates, Creator/Category Audit, and Organize draft-plan infrastructure.

The product is **not** ready to execute real user-file Apply or Restore operations. That boundary is intentional.

## Implemented

- Library path setup, scanning, indexing, folder metadata, and detail views.
- Hidden Rust-test-only Library smart-search baseline proving bundled FTS5 availability on the current macOS runtime and measuring a richer deterministic search document against today's four-field `%LIKE%` semantics. The synthetic 10k proof searches filename, creator/representative alias input, kind/subtype, embedded names, family hints, resource-summary labels, and script namespaces while deliberately excluding absolute paths; its final SQLite-vs-SQLite benchmark measured `256 ms` total for nine current-style queries versus `108 ms` for FTS5, with the deliberately difficult fixture recall@5 improving from `0.222` to `1.000`. Separate tests preserve no-answer controls for authority-seeking safety queries and explicitly record semantic wording that FTS does not understand. This is capability evidence only: production Library search, schema, commands, UI, and model/runtime dependencies are unchanged.
- Isolated developer-only local embedding benchmark completed outside the SimSuite repository using q8 `Xenova/all-MiniLM-L6-v2` in browser/WASM on synthetic data only. The measured artifact set was about `22.59 MiB` with `384`-dimension vectors; `10,000` float32 vectors would occupy about `14.65 MiB`. On the current macOS machine the first 10k embedding build took about `280.7 s`, warm cached model load about `0.92 s`, a warm query embedding about `9 ms`, and 100 warm incremental item embeddings about `3.41 s`. On the deliberately controlled 43-query fixture, exact-token FTS semantic recall@5 was `0.280` while embedding semantic recall@5 was `1.000`; this is capability evidence, not product accuracy, because the meaningful documents and queries were handcrafted together. Raw embeddings also returned a nearest-neighbour file for every safety/authority negative control, confirming that semantic retrieval must never own safe-delete, patch compatibility, malware, missing-mesh, dependency, update, or mutation truth. No SimSuite model/runtime dependency, schema, production search path, command, UI, or player-file access was added. The later deterministic fuzzy/trigram proof below shows that embeddings are not needed merely to handle ordinary typos or partial mod/creator names; their remaining case is genuinely semantic retrieval and later visual similarity. See `docs/planning/LIBRARY_SMART_SEARCH_MODEL_OPPORTUNITY_V1.md`.
- Hidden Rust-test-only deterministic fuzzy/trigram search proof now strengthens the non-model baseline without changing production Library behavior. The current bundled SQLite accepts its built-in FTS5 trigram tokenizer. The prototype retrieves at most `80` trigram candidates, preserves up to `20` strict FTS candidates, and reranks only that bounded set with camel-case-aware normalized Levenshtein/prefix similarity and a `0.72` prototype minimum score. On a `10,000`-item stress run, a standalone trigram index built in about `263 ms`; `23` holdout-style typo/partial/vague-lexical/short/ambiguous queries took about `129 ms` total through the bounded fuzzy path, with `16.0` candidates inspected on average and `80` maximum. Strict FTS recall@5/MRR on those holdouts was `0.435/0.435`; fuzzy/trigram was `1.000/1.000`, including typo recall `0.000 -> 1.000` and partial-name recall `0.286 -> 1.000`. The original exact/alias cases remained perfect, explicit safety/authority queries still return no answer through the benchmark gate, and semantic controls such as `rose kids hairstyle` and `game error helper` remain unresolved, preserving the distinction between spelling recovery and semantic understanding. These scores are synthetic capability evidence, not real-player accuracy: the author knew the fixture contents when writing the holdout queries. Production search, schema, commands, UI, model dependencies, and player files remain unchanged.
- Hidden production-shape deterministic-search feasibility proof now maps the richer search document onto realistic Library metadata lifecycles without adding a real migration. The proof favors explicit synchronization over broad triggers: scanner-style installed-row replacement and search rebuild can commit together; selected file IDs can refresh after category/insight changes; learned creator aliases refresh every installed file for that creator; alias reassignment refreshes both the old and new creator scopes so stale ownership is removed; removed or downloads-only rows leave the search index; private absolute-path text is never indexed; stale rows are repairable; full rebuilds are idempotent; and deliberately interrupted ordinary or contentless rebuilds roll back to the previous complete index. The current bundled SQLite also supports FTS5 `contentless_delete=1`. In the `10,000`-row on-disk synthetic comparison, source tables were `4,722,688` bytes; ordinary Unicode+trigram FTS produced `12,566,528` bytes total, while contentless Unicode+trigram produced `9,424,896` bytes. That reduced total database size by `25%` versus the ordinary dual-index shape and reduced measured search-index overhead from `7,843,840` to `4,702,208` bytes (about `40%`). Contentless backfill was about `815 ms`; `100` source+search refreshes about `80 ms`; warm strict search about `206 µs/query`; and bounded fuzzy search about `11.8 ms/query` in that local run. Ordinary FTS updated 100 items faster (`26 ms`), so contentless is not a free win; it is currently the leading future migration candidate because it keeps readable Library metadata authoritative while materially reducing duplicate-text storage. These are macOS synthetic measurements only, and the synthetic `insights` payloads are much smaller than real rows that may include thumbnail/base64 media. A production implementation must project only searchable insight fields and combine seeded plus user-learned creator aliases instead of parsing/copying unnecessary media payloads during index maintenance. No production FTS tables, migration, command, UI, search replacement, model dependency, or player-file behavior changed. Native Windows/Linux, realistic database distribution, broader high-contention/process-interruption behavior, batched candidate reconstruction, real production migration/write-boundary integration, and a broader representative non-private player-query corpus remain required before any production search migration.
- Hidden independent player-phrasing search evaluation V1 now removes a major source of benchmark bias. A `36`-query player-side wording file was frozen from separate Sims mod-management/player-problem research before any expected IDs were mapped; the frozen file contains six exact-name, creator/alias, typo/partial, vague-lexical, semantic-paraphrase, and authority/no-answer questions and deliberately contains no benchmark answers. Mapping after the freeze produced `15` fair positive targets, `15` unsupported questions because the seven-item representative corpus lacks the requested subject, and `6` authority/no-answer cases; the corpus was not expanded after seeing the queries. On the unchanged seven-item corpus, strict positive-target recall@5/MRR was `0.400/0.400` and bounded fuzzy was `0.667/0.667`; fuzzy stayed `1.000` for exact names, creator/aliases, and typo/partial queries, fell to `0.333` for vague lexical wording, and remained `0.000` for semantic paraphrases. The same relevance scores held after neutral fillers expanded the index to `10,000` rows; in that run strict search averaged about `283 µs/query`, while fuzzy averaged about `12.2 ms/query` over `21` measurable target/no-answer queries and inspected about `24.4` candidates on average. All six authority questions returned no answer in the controlled run, but only four are explicitly recognized by the older benchmark authority guard; definitive crash attribution and definitive current-update intent happened to return nothing through retrieval scoring and therefore exposed the explicit routing gap addressed by the later concurrency/authority proof. No threshold, fixture text, target mapping, search rule, production search path, schema, command, UI, model dependency, or player-file behavior was changed to improve the result. This is stronger capability evidence, not real-player accuracy: the meaningful corpus is still only seven synthetic subjects, so a broader representative non-private metadata corpus remains required before production thresholds are chosen.
- Hidden contentless-search concurrency and authority-routing proof V1 now tests the future design under SimSuite's real SQLite connection shape without adding a migration. Production `AppState` opens fresh command connections with `foreign_keys=ON`, `journal_mode=WAL`, and a `5 s` busy timeout. In a temporary on-disk contentless database using those same settings, an existing reader snapshot stayed on the previous complete index while another connection changed source metadata and refreshed Unicode+trigram search rows inside one transaction; after commit, a fresh reader saw the new complete state, and the old reader saw it only after ending its snapshot. A separate bounded contention probe confirmed SQLite still serializes writers: after verifying the normal `5000 ms` timeout, the contender was changed to zero timeout only for the deterministic test and received `BUSY`/`LOCKED` while the first writer held the lock; this is lock-classification evidence, not a production wait-time measurement. A simulated source/search divergence plus interrupted contentless rebuild remained invisible as a partial index to another connection, and a later full rebuild converged search to source truth. The test-only pre-retrieval authority router now explicitly blocks all six frozen authority families before any provider callback can run: safe removal, malware, patch/version compatibility, definitive crash attribution, dependency-safe removal, and definitive current update requirement; high-certainty ambiguous safety wording also fails closed. All `30` frozen non-authority queries remain retrieval-eligible. The future contract is therefore source+search synchronization in the same owning SQLite transaction, disposable/rebuildable contentless indexes, an idempotent repair path, and one provider-agnostic authority router in front of FTS/fuzzy/future embeddings. No production DB helper, search table, migration, command, UI, model dependency, threshold, player-file behavior, or Apply/Restore authority changed. Native Windows/Linux, higher-contention, real production migration wiring, and process-interruption proof remain required.
- Hidden contentless-search migration mechanics and startup-repair proof V1 now models the smallest safe future schema lifecycle entirely inside temporary on-disk Rust-test databases. The current production migration ledger still ends at `13`; the proof uses candidate structural migration `14` only as the next-free version on this branch and does **not** reserve that number for production. Under the same production-like `WAL` + `5000 ms` busy-timeout connection shape, deliberate interruption immediately after FTS/state schema creation or after full backfill rolls back the FTS5 DDL, backfill, and migration marker together, leaving the source rows unchanged. A repeat startup ensure is idempotent when the derived index is healthy; if a known-version search-owned object is missing or malformed, startup repair drops and rebuilds only the disposable search objects from authoritative source metadata while preserving the structural migration record and all source rows. The validator now checks FTS5/contentless/tokenizer settings **and the exact declared search-column order**, because the current BM25 weights are positional; a superficially valid Unicode FTS table with missing fields or reordered weighted fields is treated as damaged and repaired. Search-content freshness is tracked separately from structural migration history by a derived fingerprint containing the search-document version plus seed, creator-learning, and category-override meaning; a fingerprint change deterministically rebuilds the index and exposes newly learned creator aliases. Feature disable drops only the search-owned Unicode FTS, trigram FTS, and derived-state objects while preserving migration history and source truth; re-enable repairs them from source. Unknown/future search state now fails closed before destructive repair: a readable future schema version remains protected even if the rest of the state-table shape has changed, and an existing state table with no recognizable `schema_version` field is left untouched as unrecognized rather than guessed repairable. A conflicting structural migration owner also fails closed. These are bundled-SQLite/macOS sandbox results only. No production migration file, `database::initialize`/`ensure_schema`, FTS table, search command, UI, ranking rule, model dependency, player-file behavior, or Apply/Restore authority changed. Native Windows/Linux migration behavior, real-process crash/interruption durability, production write-boundary integration, and broader contention remain required.
- Hidden contentless-search write-boundary integration proof V1 now maps the remaining runtime synchronization responsibilities without wiring search into production. A test-only scope calculator keeps explicitly changed file IDs even after deletion or movement out of installed scope, expands creator IDs only to currently installed Mods/Tray rows, and returns one sorted/deduplicated union. In the alias-reassignment fixture, reading the old alias owner before the upsert and combining old-owner, new-owner, and explicit reassignment scope refreshed exactly `[1, 2, 5]`; unrelated Library rows stayed untouched, and repeating the same scope did not grow the FTS tables. Exact category/searchable-insight changes refresh only their affected IDs; moving a file to `downloads` or deleting it removes only that stale search row. A deliberate rollback after changing source metadata, installed membership, scoped search rows, and the derived fingerprint restored all four together. A separate on-disk WAL scanner proof showed an existing reader remains on the previous complete Library/search snapshot while a source-replacement + full-search rebuild transaction commits, then sees only the new complete snapshot after ending its read transaction; a later interrupted replacement never became visible. Review hardening deliberately keeps scoped refresh and search-state `ready` advancement as separate operations so a caller cannot automatically mark an incompletely refreshed index as synchronized. The production audit originally identified two prerequisites rather than hiding them: lazy special-mod/profile insight persistence can change searchable fields, while move/restore membership-record changes still need a safe SQLite source+search synchronization point that does not weaken file backup/rollback rules. The follow-on persistence work below has now resolved both per-file error ownership and multi-file atomic grouping for that special-mod insight boundary; move/restore membership synchronization remains the next production write-owner gap before search can safely attach. Thumbnail-only detail persistence does not require search refresh because thumbnails are not indexed. Latest full Rust evidence after this proof registered `539` tests with no failures and the same `5` intentional large stress ignores. No production migration/table, command, UI, Library search behavior, ranking threshold, model/runtime dependency, player-file access, or Apply/Restore authority changed. - Special-mod multi-file insight transaction ownership V1 is now production database behavior, but it does **not** enable smart search. Both lazy refresh paths use the same two-phase pattern: inspect and merge candidate `FileInsights` before opening a write transaction; for indexed rows capture the exact raw `files.insights` JSON that the proposal was prepared from; then open one short shared-connection transaction and update every indexed row with `WHERE id = ? AND insights = ?expected`. A missing/stale row or any later database failure aborts the whole transaction, so earlier writes in the same batch roll back. Only after commit are the caller-owned `ProfileFile` / `ExistingInstallFile` values updated in memory. Existing and preserve installed-file candidates share one batch, and disk-only `file_id=None` files remain memory-only but also wait for any indexed siblings to commit before their memory advances. Regression tests prove two changed indexed rows commit together; a forced failure on the second update rolls back the first and leaves all memory old; stale prepared evidence cannot overwrite a newer database value; a changed MCCC row still writes exactly once and an unchanged repeat performs no second `UPDATE`; forced one-row failures remain visible through the real load path; disk-only-only refresh remains memory-only; and a mixed disk-only + indexed batch leaves both memory values unchanged when the indexed write fails. Existing special-mod assessment/version behavior, including live-archive version refresh, remains green. The current special-mod call sites were audited as outside another SQLite transaction, so this short batch does not hold a database write lock while package/archive inspection runs. A future smart-search scoped refresh may join this same transaction only after a production search schema exists. No FTS migration/table, production Library search, search command/UI, model dependency, player-file mutation, or Apply/Restore authority was added.
- Hidden Rust-test-only move/restore membership transaction proof V1 now closes the next database-side design gap without changing the real move engine. `move_engine_membership_prototype.rs` is doubly test-gated, uses SimSuite's production SQLite schema entirely in memory, has no filesystem calls, and is not registered as a Tauri command. Its coordinator treats the current row's file ID, path, Library location (`mods` / `tray` / `downloads`), and Downloads ownership as the evidence that must still match before a membership change is accepted. The tests prove that Downloads -> Mods/Tray installs only the intended row while preserving its ID; Mods/Tray -> Downloads removes only that row from installed membership; delete removes exactly the intended row; a deleted old installed file may later be restored as the same semantic Library member under a new database ID; several membership changes commit together; a forced failure on the second database write rolls the first one back; newer ownership evidence that changes path, Library location, and Downloads ownership is preserved while the stale instruction fails closed; and repeating an already-completed reconciliation is harmless. This also records the identity rule needed by any future search integration: follow the Library's current rows rather than assuming a historical file ID always returns after restore. The production audit still shows the existing move/rollback flows changing real files first and then repairing database rows individually, so no production move/restore transaction refactor is claimed here. No player-file operation, production Library search, FTS table/migration, model dependency, Tauri command, or real Apply/Restore authority was enabled by this proof.
- Hidden file-operation -> Library-membership handoff proof V1 now joins the existing fixture-only move/recovery journal to the database-only membership coordinator without wiring either into production. The proof currently covers same-row moves such as Downloads -> Mods: before Library membership may advance, the durable attempt must already be at `source_release_completed` (or an already-finished `committed` repeat), the recorded source must be absent, and the destination must still match the attempt's expected hash and size. Path identity is resolved before comparison so macOS aliases such as `/var/...` and `/private/var/...` are not falsely treated as different files. All filesystem/path/hash work happens before the SQLite write transaction; once that short transaction opens, SimSuite rechecks the prepared attempt and ApplyPlan-item database evidence, applies the stale-safe Library membership compare-and-set, and changes the attempt from `source_release_completed` to `committed` in the same transaction. The generic attempt-state helper can no longer declare `committed`, preventing test code from bypassing that handoff. Tests prove successful/repeated handoff, changed-destination rejection before any database claim, stale/newer Library ownership preservation, and a two-file case where an injected failure while committing the second attempt rolls back both Library membership changes and both `committed` markers while the already-moved fixture files remain at their verified destinations for later recovery/retry. After removing the injected failure, the same batch retries successfully. The proof deliberately does **not** claim filesystem + SQLite atomicity: another process could still alter a file in the small interval after pre-transaction verification and before/after the database commit, so production needs explicit post-crash/restart verification and recovery policy rather than assuming that gap can disappear. It also does not yet connect replacement deletion/new-ID restore membership to the attempt journal. Latest Rust evidence registers `556` tests: `551` pass and the same `5` large synthetic stress tests remain intentionally ignored. No production move engine, player-file behavior, Apply/Restore command, smart-search path, migration, or model dependency changed.

## Recent backend provenance gate

Plan Hash / Provenance V1 is now implemented for newly saved ApplyPlans. The backend computes a SHA-256 hash over a canonical preview identity that includes source scope, preview-time folder configuration, context trail, saved item/source/destination data, item signals/blockers, source file snapshots, and active rule/seed/settings version evidence. Provenance distinguishes `backend_generated_sorting_preview` from `client_supplied_preview`; future confirmation must accept only backend-generated provenance. Full provenance stays server-side; normal frontend responses expose only hash metadata. The hash/provenance columns are immutable once set. Validation blocks future confirmation if the stored hash/provenance is missing or no longer matches the persisted preview snapshot. This does not enable Apply, Restore, backup execution, confirmation tokens, result logs, restore logs, folder creation, or file mutation.
